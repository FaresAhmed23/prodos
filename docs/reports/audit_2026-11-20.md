### c) `Alert.lang` composite PK — REFUTED as described, but a worse variant is real

`backend/app/models.py:55` declares `alert_id` as the **sole** primary key.
`lang` at line 65 is a plain nullable `String(8)` column. `alerts.py:72-81`
omits it, which is legal. So:

- Alert inserts are not blocked by `lang`.
- `alert_id` remains unique, so `PATCH /alerts/{id}` (`routers/alerts.py:96`),
  cursor paging (`pagination.py:37` keys on PK), and the
  `incidents.explained_alert_id` FK all still behave.
- The `alert_texts` table mentioned in
  `ai/Context_builder/Database/alert_queries.py:14` does not exist. Translation
  storage currently lives only in `explanation_logs`.

**The real break is `ExplanationLog`.** `backend/app/models.py:84-85`:

```python
lang: Mapped[str] = mapped_column(String(8))
site_id: Mapped[str] = mapped_column(String(64), ForeignKey("site_profile.site_id"))
```

Both are non-nullable with no default. `backend/app/alerts.py:85-96` constructs
`ExplanationLog` without either. On any migrated database the insert raises
`NOT NULL constraint failed` / Postgres `not-null violation`. Because
`alerts.py:61-97` uses one session and one commit, the `Event` and `Alert` rows
roll back with it, and `events_ingest_loop` (`mqtt.py:136-142`) catches, logs
"event ingest failed", and reconnects. **No alert is ever created.**

Also: `alerts.lang` is absent from the only migration, so on a migrated
database `SELECT alerts.*` fails — that is the 500 Arsany documented in
`frontend/src/App.tsx:300-306` ("SQLite migration issue with alerts.lang").

  components, window).

  model, but `SensorCreate`/`SensorUpdate`/`SensorOut`
  (`schemas.py:115-138`) omit it. Adding it edits the CONTRACT file that
  `detection/schemas.py` mirrors. Alternative: a small REST-only model or a
  dedicated `PATCH /sites/{id}/sensors/{sensor_id}`.
- **Events are not attributed to a site.** `alerts._store()`
  (`alerts.py:61-71`) writes `Event` without `incident_id`, and nothing else
  links an event to a site. The `Context_builder` incident manager would do it,
  but it is unwired (§3e). Threat exposure cannot be scored per site until
  either (a) the incident path is wired into `_store`, or (b) scoring resolves
  site from `event.sensor_ids` through `Sensor.site_id` at read time.
- **Retention vs window conflict.** `retention_days` default 7
  (`config.py:10`), score window default 30 days. `frames` older than 7 days
  are deleted (`retention.py:17-36`), so monitoring-coverage and batch-gap
  components cannot cover a 30-day window without either raising retention,
  changing the window, or storing daily aggregates. This needs a decision.
- **`alerts` has no `site_id`** and no `lang`-independent join to a site.
  Response scoring must join alert → event → incident → site, which is only
  populated once §3e is fixed.
